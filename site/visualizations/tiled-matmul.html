GPU/TPU algorithms: blocking matrix multiplication

A preview based on the available deck GPUS and TPUs 24Nov2026, slides 1–4. The November 17 lecture transcript mentions a possible session on GPU/TPU algorithmic principles; this does not establish that the material was actually taught or will be part of Exam 2.

Why tiles matter

For Z=X×Y with n×n matrices, the source contrasts a straightforward computation using O(n³) arithmetic and potentially O(n³) repeated memory fetches with blocked multiplication. Let b divide n and q=n/b. There are q³ block multiplications; each ideally reads O(b²) input elements, giving O(n³/b) input fetches, while total scalar multiplication work remains Θ(n³).

The model below counts two input tile reads per block multiplication, one output-matrix write at the end, and storage for two input tiles plus one output accumulator tile. It is an idealized data-movement model, not a hardware speedup prediction. Real cache size, occupancy, memory hierarchy, tile reuse, write traffic, matrix layout, precision, and synchronization change the result.

Source example and boundary reasoning

The slide compares n=1000, b=500 with n=1000, b=100. This simplified model predicts ideal input-fetch reduction factors 500 and 100 respectively, but the b=500 case needs 25 times as much tile storage as b=100. The slide's approximate cache footprints are for a single tile, so a complete implementation must also accommodate the other input and accumulator tiles.

Counterexamples to careless reasoning: When b=1, tiling gives no reduction in this model. Increasing b beyond available fast memory breaks the assumed reuse, and b that does not divide n needs boundary/padding handling absent from the current demonstrator. A change in operation count or actual wall-clock speed is not implied by the ideal fetch count.
